# ЕСТУ: структура проекта

## Запуск

Запускайте из корня проекта через `ESTU START.cmd`. Для разработки можно открыть PowerShell в папке проекта и выполнить:

```powershell
& .\server\runtime\python\python.exe -X utf8 .\server\portable_server.py --port 8180
```

Откройте `http://127.0.0.1:8180/`. Без HTTP-сервера модульный интерфейс не запускается. Сборщик, Node.js и отдельный сервер базы не нужны. Для изолированной разработки пользуйтесь отдельной папкой без рабочей базы и файла `server/yandex-forms.config.json`.

## Карта проекта

| Где | Что отвечает |
| --- | --- |
| `index.html` | Разметка и точка подключения интерфейса |
| `frontend/main.js` | Запуск и явная связь модулей интерфейса |
| `frontend/core/` | HTTP-клиент, состояние, доступ, переключение экранов и обновление данных |
| `frontend/features/` | Авторизация, журнал, карточки заявок, история, парк, склад, смены, профили и отчёты |
| `frontend/animation/` | Холсты троллейбуса, привязка контактной сети и стили сцены |
| `frontend/styles/`, `assets/` | Стили интерфейса и ресурсы |
| `frontend/shared/xlsx.js` | Формирование XLSX, отдельно от получения данных отчёта |
| `server/portable_server.py` | Локальный HTTP-сервер, публичные файлы, запуск фоновых задач |
| `server/estu_api/` | HTTP-маршруты по разделам, проверка сеанса, статусы и ответы |
| `server/estu_services/` | Операции с парком, заявками, историей, оборудованием и снимком состояния |
| `server/portable_workflow.py`, `portable_stock.py` | Правила движения заявок и складских операций |
| `server/portable_core.py`, `portable_schema.sql` | SQLite, базовые таблицы, сеансы и права |
| `server/portable_yandex.py`, `server/navcontrol/` | Интеграция с формами и обработка навигационных отчётов |
| `server/tests/` | Серверные тесты на временных базах |

`portable_modules.py` оставлен как совместимый импорт для старых тестов и служебных скриптов. Новые серверные вызовы используют `estu_services` напрямую. `server/data` содержит данные, а не исходный код. Сервер отдаёт в браузер только `index.html`, `frontend` и `assets`; выгрузки выдаёт через авторизованный API.

## Как проходит запрос

1. Экран в `frontend/features` собирает поля и вызывает `core/api.js`.
2. `estu_api` определяет маршрут и проверяет сеанс. Маршрут разбирает запрос и вызывает нужную операцию.
3. Сервис проверяет доступ и правила, использует транзакцию SQLite и возвращает результат.
4. `core/refresh.js` получает свежий снимок `/api/state`, а `main.js` связывает обновление с нужными экранами. Черновики форм сохраняются при фоновом обновлении.

Например, передача заявки: `features/request-flow.js` → `estu_api/requests.py` → `portable_workflow.decide`. Складские операции проходят через `estu_api/stock.py` → `portable_stock.py`. Анимация не знает о заявках, сеансах и API. Модули браузера используют явные импорты без циклов; связь с переключением экранов передаётся при запуске.

## Правила дальнейших изменений

- Правило доступа или расчёт остатков меняется на сервере. Интерфейс только показывает доступные действия и результат.
- Новый экран подключается в каталоге, оболочке и соответствующем модуле раздела. Не добавляйте зависимость анимации от состояния заявки.
- Не смешивайте перемещение файлов с изменением схемы базы или правил ремонта. В этой переработке схема и данные не менялись.

```powershell
& .\server\runtime\python\python.exe -X utf8 -W ignore::ResourceWarning -m unittest discover -s .\server\tests -v
```

Правила маршрутизации, склада и Excel описаны отдельно: [заявки](REQUEST_ROUTING.md), [склад](WAREHOUSE.md), [отчёты](EXCEL_REPORTS.md).
